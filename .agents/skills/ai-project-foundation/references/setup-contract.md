# Setup contract

Read for every setup/adoption run. The entrypoint owns mode selection; this reference owns setup scope and completion. User exclusions and existing authorization take precedence.

## Scope

`setup` means create or repair the destination's Markdown instructions and project-local AI-agent skills, then have the relevant agent review their content against the source. Every normal setup installs the five skills listed in [the bundled standard manifest](../assets/project-skills/manifest.json): `test-engineering`, `security-review`, `graphify`, `hook-management`, and `impeccable`. The Foundation installer skill is not part of that count. An explicit `documents-only` limit remains in force and must be recorded as an exclusion. Foundation authors no checker/helper scripts, Git hooks or CI gates. The full Impeccable v4.7.0 package contains five upstream `.js` support files; preserve them as package-owned resources. Copying the skill does not install its separate CLI engine or configure hooks. Existing project-native commands remain owned by the project and run only when its rules or the task require them. Executable automation is outside this workflow.

Treat skills as required setup deliverables, not optional references. The fixed standard list is exactly the five names and asset paths in `assets/project-skills/manifest.json`; do not substitute host-only skills or unbundled files. User-requested extras and additional normal-workflow routes are listed separately and increase the selected total. Do not scan unrelated host skills. Before writing, record each selected skill's name, owner/source, intended scope, target path, invocation policy and observed state in `skillInventory`. A skill routed in the project guide is selected and must be installed at that scope or setup remains partial. The manifest's `requiredSkills` and `skillPaths` must match every project-local deliverable. For each inventory entry, record `name`, `scope` (`project` or `host`), `source`, `path` (project-relative or a non-machine-specific host label), `invocationPolicy`, `installed` and `discoverable`.

For an explicit project-only request, install every selected project workflow skill under a supported project-local path (normally `.agents/skills/<name>`). An existing host installation may supply the source files, but it does not count as a project-local installation. Do not install, configure or modify global skills/settings; preserve their exact pre-setup state. Copy a complete upstream skill folder, including all package-owned files and referenced resources, only when its license and host support allow it. `SKILL.md` or the transitive set of linked Markdown files alone is not the package. If a selected skill cannot be installed or discovered locally, keep the route truthful and report partial setup with the exact gap; never silently omit it or route to a nonexistent capability.

Discover only named upstream skills, executables or services needed by a required/applicable deliverable; do not inventory every host skill, service or installation directory. Verify each selected dependency using the supported catalog and exact relevant install locations. Record installed, discovered, configured, invoked and verified separately. If files exist but discovery omits them, inspect metadata and invocation policy; explicit-only skills are not automatic routes. Repair only the project-local route when supported. Changing global settings or refreshing the host requires its actual supported mechanism. Never claim discovery from disk presence alone or assume an upstream skill exists without evidence.

Preserve skills owned by the host, upstream authors or the project. Before changing a skill location, record the names and paths in that exact target directory and capture selected skill files, settings and callbacks. Install or update only the exact Foundation-owned skill directory through the supported mechanism; never replace or clear a parent skills directory. Do not remove, rename, disable or overwrite another skill. If a selected installed skill such as Impeccable is missing or changes unexpectedly after setup, restore it from the captured pre-setup state or supported host route, verify its discovery, and report any unresolved loss as incomplete setup.

## Skill package integrity

Use this check for every selected skill intended to satisfy a project workflow, whether it already exists or will be newly installed/updated. It proves package completeness at the declared scope; host discovery and semantic suitability remain separate checks.

1. Identify the authoritative source: repository plus immutable commit/tag, bundled asset revision, or a captured pre-install directory when that is the authorized source. Record the source and revision in `skillInventory`; a branch name or unversioned URL alone is not an immutable reference.
2. Before editing the destination, recursively list every file and symlink inside the skill folder using normalized relative paths and calculate SHA-256 for each file. Include hidden files, nested references/assets, package-owned scripts and binaries regardless of extension. Record symlink targets and verify they stay inside the package; if the destination cannot preserve a required symlink, report that exact gap. Exclude only files outside the selected skill folder, such as the enclosing repository's `.git` directory. Do not filter by extension or by whether a file is linked from `SKILL.md`.
3. Install the full source folder before applying project-specific adaptations. Recompute the destination inventory the same way. Compare path sets, symlink targets and per-file hashes. The inventory fingerprint is SHA-256 over UTF-8 text with one record per entry: `file<TAB>relative/path<TAB>lowercase-file-sha256` or `symlink<TAB>relative/path<TAB>target`. Normalize path separators to `/`, sort records by ordinal relative path, join with LF and end with LF. Record source/destination entry counts and fingerprints; list missing, changed and added relative paths. For a source that cannot be inventoried or read, do not claim package completeness.
4. Preserve every source file. A changed source file is acceptable only when its project adaptation is necessary, recorded with the path and reason, and reviewed against the upstream guidance. Added files must be identified as project-owned adaptations. An unexplained missing, changed or added file makes installation incomplete until resolved. For an exact upstream copy, both inventories must match with no differences.
5. Open the installed `SKILL.md`, validate its `name` and description, and resolve all relative file links from the relevant instructions. When `agents/openai.yaml` exists, inspect its invocation policy, declared dependencies and interface metadata; preserve supported fields and verify routes reflect the actual policy. Confirm all referenced resources exist and that the project guide points to the declared target. This semantic/link review does not replace the complete file inventory. Keep runtime discoverability, invocation policy, and whether the skill was actually invoked as separate states.

Record `sourceRevision`, `sourceFileCount`, `sourceInventorySha256`, `installedFileCount`, `installedInventorySha256`, `missingFiles`, `changedFiles`, `addedFiles`, `approvedChanges`, and `inventoryVerified` for every project skill in `skillInventory`. Use empty lists for no differences; do not omit fields to hide an unchecked state. The checklist summarizes the source and destination counts/fingerprints and exact differences. It counts installation completeness independently of runtime discovery.

Keep deployment, publication, external tracker writes, global installation/settings and timed background jobs within separately provided scope. Preserve existing automation and disabled states; this workflow does not install or configure hooks.

Use `PRODUCT.md` and `CONTEXT.md` as the default canonical paths. Honor an explicit user exclusion by recording its reason in the delivery list and manifest. For unknown product intent, create a useful status record that separates owner-approved statements, source observations and unresolved choices; do not invent acceptance. For an empty domain glossary, create a short explicit “no confirmed project-specific terms yet” state without adding general programming vocabulary. An unsettled consequential product choice blocks that choice, while independent setup work continues.

Maintain a [document delivery list](document-blueprints.md#document-acceptance)
with required/applicable/excluded/not-applicable classification and reason. Reuse
canonical documents when they already satisfy the contract. Fill missing or
insufficient required content in this run; a file count, empty template, deferred
next command or link back to the whole source does not fulfill that content.

## Perform the setup

1. Build one deliverable list from the request, source, prior open reviews and applicability table. Mark each item required, applicable, excluded or not applicable with a reason, and list its canonical target path. For normal setup, name all five standard skills and their project-local scope before setup; add requested extras separately. Copy [the foundation manifest template](../assets/foundation-profile.template.json) to `docs/agents/foundation.json`; keep `documents` aligned with every required/applicable canonical document and internal skill contract, `requiredSkills`/`skillPaths` aligned with the five standard skills plus selected extras, and `skillInventory` complete for every selected skill. Copy [the skill checklist template](../assets/skills-checklist.template.md) to `docs/agents/skills-checklist.md` and set `skillChecklist` to that path; list the five exact standard skill names and report standard count, total selected count, complete count, and incomplete count. For explicit `documents-only`, do not change skills or their manifest/checklist; record the five standard skills as excluded by the user's scope. Keep any existing files aligned with the scope and delivery list.
2. Load only the references and existing upstream instructions needed by that list. Do not install dependencies or tools for standard Markdown/AI-agent setup. If the user explicitly selected an executable capability, follow its supported setup instructions and report unavailable prerequisites accurately.
3. Create or repair every required document and, for normal setup, all five skill folders from their owners/bundled assets, then fill documents with evidence from the destination source and accepted owner decisions. Create `AGENTS.md`, the one-line `CLAUDE.md`, `PRODUCT.md`, `CONTEXT.md`, `DESIGN.md`, and `SECURITY.md` on every setup unless explicitly excluded; unknown facts become explicit status/evidence/owner records. Create the foundation report as a working draft with delivery rows and a pending final-review entry. Replace template placeholders with verified content or a clearly owned open item. Archive and rebuild existing instructions using [document blueprints](document-blueprints.md#instruction-migration). In normal setup, follow the [skill installation contract](secure-testing-workflows.md#install-or-repair-the-project-skills), copy all five manifest-listed folders to `.agents/skills/<name>`, and record their exact names/paths and required internal contracts in the manifest/checklist. In `documents-only`, preserve existing skill paths and record the standard bundle as excluded. Compare complete source/destination inventories and record differences per the integrity contract; do not treat a host-global copy as satisfying a project-local request. Copying Graphify does not install its CLI; copying Impeccable does not install its separate engine or run its launcher. Installing hook-management or Impeccable does not configure hooks. When upgrading an older Foundation install, remove legacy Foundation-owned checker artifacts and references and verify their absence using the [AI-agent review migration steps](ai-agent-review.md#upgrade-from-an-older-foundation-install), preserving upstream Impeccable support files. Preserve every unrelated host/upstream/project skill and verify each selected skill remains installed and discoverable at its declared scope. Adapt invocation policies only to verified capabilities. Verification skills inherit mandatory gates rather than redefining them.
4. Create Markdown criteria and route them to the relevant AI-agent skill. Preserve any existing project automation and disabled states unchanged. This setup does not add tools, dependencies, hooks or executable checks.
5. Trace one current journey through its requirement, source and acceptance scenario. Have the appropriate AI skill review the implementation and report file/line evidence. Run existing project-native commands only when repository rules or the current task require them; distinguish those results from the AI review.
6. Have the AI agent review the foundation manifest and delivery list against the destination: open every required/applicable path, inspect all declared project skill folders and their internal contracts/resources, follow their local links, and compare every selected package's recursive path/hash inventory with its recorded source. Confirm the manifest and checklist list exact missing/changed/added paths and explain every approved adaptation; verify each declared project skill is locally discoverable and callable according to its invocation policy. Repair unexpected loss only through the supported project-local route or leave setup partial with exact paths and evidence. Confirm no global install/settings changed when project-only was requested. Do not use a bundled JavaScript checker as the project's review mechanism.
7. Finalize the foundation report with per-deliverable status, changes, AI review evidence, any required existing project command results, blockers and continuation. Keep the final-review result structure stable when filling its pending entry. Review semantic consistency separately from file/path presence. Record owned fixture/process cleanup or exact leftovers/blocked cleanup; retain useful evidence outside disposable code with its durable-storage limits.

For explicit-only upstream skills, preserve their invocation/confirmation rules. Reading their templates may support local configuration without claiming that workflow was invoked. Reuse choices already settled by the user; if a prerequisite choice remains consequential, present a concrete draft while completing independent work.

## Completion

- **Complete local setup:** every required/applicable document exists, the AI-agent review covers its content against the source, and local links resolve. Any project-native checks required by existing rules pass. Clearly identify fresh-session or remote outcomes not observed; do not describe them as verified.
- **Partial setup:** required work is still absent or checks have not passed. Name the incomplete deliverables, remedy attempts and next action; continue work while progress is possible.
- **Blocked setup:** a concrete prerequisite prevents the remaining required work. Identify the blocking action/platform limitation and finish independent deliverables first.

Recording `unavailable`, `not configured` or `next action` is evidence reporting, not fulfillment of a required deliverable. Any required canonical document (`PRODUCT.md`, `CONTEXT.md`, `DESIGN.md`, or `SECURITY.md`) being absent because facts were unknown is incomplete; its explicit unknown-state record fulfills the documentation deliverable without making unsupported claims. Any unexplained missing skill-package file or unchecked inventory is incomplete. An omitted local standard skill because “scope was not separately agreed” is not a valid blocker when normal setup already authorized it.
